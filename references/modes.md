# 五种模式完整流程

本文是 `SKILL.md` 的展开，供需要执行细节时阅读。

## CREATE

**适用**：用户要创建全新技能，或对话中出现了一段值得固化的工作流但还没到 CAPTURED 的自动化程度。

**步骤**

1. 捕获意图，四个必答项：
   - 这个技能要让 Agent 能做什么？
   - 什么时候该触发它？
   - 期望的输出格式是什么？
   - 要不要建测试用例？（有客观产出的要建；纯主观风格的可不建）
2. 起草 `SKILL.md`，遵循 [writing-guide.md](writing-guide.md)。
3. `init` 建立工作区与进化记忆。
4. 写 2-3 条**真实**测试用例：口语化、带细节（文件名、列名、公司名），
   不要写「格式化这份数据」这类抽象请求——太简单的请求模型自己就能做，测不出技能价值。
5. 跑 with_skill 与 without_skill 两组，落盘 `grading.json` / `timing.json`。
6. `benchmark` 聚合，把结果给用户看，按反馈迭代。
7. 迭代到满意后 `package`，并在进化记忆写一条 CAPTURED 日志。

**完成标准**：有测试用例、有基线对比数据、有至少一轮用户反馈。

---

## EVALUATE

**适用**：想知道技能好不好用；或改动前后要对比效果。

**要点**

- 两组并行跑（with_skill + 基线），不要先跑一组再补另一组——时间差会带来环境漂移。
- 基线选择：
  - 新技能 → `without_skill`（完全不用技能）
  - 改进已有技能 → 改动前先 `cp -r <skill> <workspace>/skill-snapshot/`，基线用 `old_skill`
- 断言写**可客观验证**的：文件是否生成、字段是否正确、工具是否按序调用、耗时是否超阈值。
  能写脚本校验的就不要靠肉眼。
- `grading.json` 的每条断言必须包含 `text` / `passed` / `evidence` 三个字段。
- 跑完看 `benchmark.md` 末尾的「观察」，重点两类问题：
  - **区分度不足**：各配置通过率完全相同 → 这条用例测不出技能价值，换掉
  - **方差过大**：标准差 > 0.2 → 结果不稳定，可能用例本身有歧义

## FIX

**适用**：技能执行中出现退化；信号积分 ≥5；或「用户纠正 + 用户澄清」同时出现。

**流程（最多 3 轮）**

### 阶段一：诊断

1. 读 `SKILL.md` 及其引用资源，建立完整理解
2. `scan` 查结构问题，`health` 查记忆 / 信号 / 历史基准
3. 五维评估，各 1-5 分：有效性 / 性能 / 稳定性 / 可测试性 / 体验
4. 针对最低分维度做根因分析：
   - 失败点：引用对话里的实际片段，说明它具体在哪一步错了
   - 根因归类：缺少知识 / 错误假设 / 指令歧义 / 边界缺失 / 流程冗余 / 交互不友好
   - 期望 vs 实际：用户想要什么，技能交出了什么
   - 纠正路径：用户是怎么把它引导到正确答案的？这段引导能否内化进技能
5. **先读进化记忆**，确认这个方向没失败过

### 阶段二：生成方案

`python scripts/skill_cli.py report <技能路径> --mode FIX`

每条修改必须写清：

- 改进维度 + 优先级（紧急 / 重要 / 建议）
- 位置（SKILL.md 的具体章节）
- 当前内容 → 修改为（精确引用，可直接替换）
- 理由：为什么这样能解决根因
- 回归风险：可能破坏哪些已有正确行为

**写作原则**：解释「为什么」，而不是堆大写的 MUST。模型理解原因后表现更好，
也不容易造成过度僵化的过拟合改动。

### 阶段三：验证

构造 2-3 个场景模拟验证：

| 场景类型 | 验证目标 |
|---|---|
| 原始失败场景 | 本次触发进化的问题是否修好 |
| 已知正常场景 | 之前能处理的场景有没有回归 |
| 边界场景 | 修改可能波及的边界情况 |

- 全部通过 → 呈现给用户，建议应用
- 回归失败 → 回到阶段二，最多 3 轮
- 部分通过 → 拆开，通过的部分先上

### 阶段四：应用

**用户确认后**才改文件，精确替换而非整文件覆盖。然后：

```bash
python scripts/skill_cli.py defect-to-eval <技能路径> --index 1 --resolve
python scripts/skill_cli.py health <技能路径>
```

并在进化记忆追加 FIX 日志，写清「教训」供下次参考。

## DERIVED

**适用**：技能整体能用，但某个子场景总是处理不好；且该子场景值得专门优化。

**与 FIX 的区别**

| 维度 | FIX | DERIVED |
|---|---|---|
| 产出 | 原技能的新版本 | 新技能目录 |
| 适用 | 指令有 bug 或退化 | 整体 OK，某子场景需要专门处理 |
| 关系 | 替换旧版本 | 与父技能共存，覆盖更窄场景 |

**流程**

1. 从对话中提炼父技能搞不定的具体子场景
2. 创建新 `SKILL.md`：
   - `description` 写明「是 `{父技能}` 的衍生版本，专用于 `{子场景}`」
   - 触发关键词比父技能**更窄更精确**，只在子场景被选中
   - 可引用父技能内容，但聚焦子场景的特殊处理
3. 验证触发关键词不与父技能冲突
4. 用户确认后创建目录并登记

## CAPTURED

**适用**：对话中出现了「≥3 轮交互解决一个完整问题，且没有现成技能覆盖」的过程。

### 四维价值评估

| 维度 | 达标标准 |
|---|---|
| 新颖性 | 现有技能中无同类方案 |
| 可复用性 | 预期复用频率 ≥ 每月 1 次 |
| 复杂性 | 涉及 ≥3 个步骤或专业知识 |
| 可泛化性 | 可用参数替代硬编码值 |

≥3 维达标，或检测到 ≥2 个高价值捕获信号时，主动提示用户。

### 提炼：信号 vs 噪声

**保留**：领域规则、决策标准、工具使用模式、边界情况、MCP 依赖
**丢弃**：笔误、跑题讨论、调试死胡同、个人偏好

提炼路径：问题描述 → 解决步骤 → 关键决策点 → 领域知识 → 边界情况 → 工具依赖。

### 工作流

```bash
python scripts/skill_cli.py capture my-skill --dir ./skills --summary "一句话说明"
python scripts/skill_cli.py init ./skills/my-skill
python scripts/skill_cli.py eval-add --workspace <ws> --prompt "真实用户会说的话" --expected "..."
```

捕获产出的是**草稿**，必须补测试用例并做基线对比，合格后才算正式启用。
